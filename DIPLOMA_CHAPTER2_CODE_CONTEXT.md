# Контекст кода проекта для написания главы 2 диплома

Этот документ предназначен для передачи в ChatGPT с функцией глубокого анализа, чтобы на его основе можно было написать вторую главу дипломной работы по теме разработки платежного шлюза. Документ описывает фактическое состояние кода проекта, его архитектуру, используемые технологии, структуру модулей, жизненный цикл платежа, работу адаптеров, базу данных, API, тестирование и эволюцию реализации.

Основной фокус документа: программная архитектура, проектирование подсистем, взаимодействие компонентов, реализация бизнес-логики, структура данных и технологические решения. Аспекты информационной безопасности упоминаются только там, где они непосредственно влияют на программную архитектуру, но не являются главным предметом описания.

## 1. Общая характеристика проекта

Проект представляет собой прототип платежного шлюза, реализованный на языке Go. Шлюз предназначен для приема платежных запросов от интернет-магазина, выполнения первичной обработки платежа, выбора внешней платежной системы, передачи платежа в соответствующий адаптер, сохранения состояния транзакции и предоставления результата через API.

В рамках проекта реализуется не монолитная функция оплаты, а набор взаимосвязанных подсистем, каждая из которых отвечает за отдельный этап жизненного цикла платежа:

- HTTP API для приема запросов;
- модуль валидации платежных данных;
- оркестратор платежей;
- модуль антифрода;
- модуль токенизации;
- маршрутизатор платежей;
- адаптеры внешних платежных систем;
- модуль обработки webhook-уведомлений;
- сервис уведомлений интернет-магазина;
- модуль логирования;
- PostgreSQL-хранилище;
- подсистема отчетов и статистики;
- подсистема возвратов платежей.

Проект поддерживает несколько вариантов платежных систем:

- YooKassa через redirect-сценарий;
- PayAnyWay через платежную форму MONETA.Assistant и тестовый режим;
- эмуляционный адаптер цифрового рубля;
- симулированный адаптер для локальных проверок и тестовых сценариев.

Цель архитектуры состоит в том, чтобы отделить бизнес-логику платежного шлюза от конкретных провайдеров. Внешние платежные системы подключаются через адаптеры, а оркестратор работает с ними через общий интерфейс. Благодаря этому можно добавлять новые платежные системы без переписывания всего жизненного цикла платежа.

## 2. Технологический стек

Проект написан на Go. В `go.mod` указан модуль:

```text
payment-gateway
```

Основные технологии и библиотеки:

- Go как основной язык серверной разработки;
- стандартная библиотека Go для HTTP-сервера, JSON, контекста выполнения, времени, криптографических и сетевых операций;
- PostgreSQL как основная база данных;
- `github.com/jackc/pgx/v5` для подключения к PostgreSQL и выполнения SQL-запросов;
- `github.com/go-kit/kit` для организации endpoint-слоя и HTTP-транспорта;
- `github.com/go-playground/validator/v10` для декларативной и программной валидации DTO;
- `github.com/skip2/go-qrcode` для генерации изображения QR-кода в эмуляторе цифрового рубля;
- PowerShell-скрипты для запуска проекта, администрирования мерчантов, работы с маршрутами и проверки состояния БД;
- Postman collection/environment для ручного тестирования API, формирования HMAC-подписей и визуализации ответов;
- optional Vault Transit для защиты некоторых секретов, но это не центральная тема архитектурного описания второй главы.

Проект можно запускать локально через PowerShell-скрипты. Основной исполняемый вход находится в:

```text
cmd/payment-gateway/main.go
```

## 3. Архитектурный подход

Проект построен как модульный backend-сервис с RESTful API и внутренней слоистой декомпозицией.

Ключевая идея архитектуры: HTTP-слой не должен напрямую знать детали работы платежных систем, базы данных или антифрода. Он принимает запрос, извлекает контекст, выполняет авторизацию на уровне middleware и передает управление оркестратору. Оркестратор последовательно вызывает независимые подсистемы через интерфейсы.

Архитектура разделяет следующие уровни:

- транспортный уровень: HTTP handlers, go-kit endpoints, middleware;
- прикладной уровень: оркестратор платежей и обработчик возвратов;
- доменный уровень: DTO, статусы платежей, контракты интерфейсов;
- инфраструктурный уровень: PostgreSQL-хранилища, адаптеры провайдеров, webhook-уведомления, логирование;
- инструментальный уровень: PowerShell-скрипты, Postman-коллекция, проверочные SQL-файлы.

Такой подход близок к принципам hexagonal architecture: центральная бизнес-логика работает с абстракциями, а внешние системы подключаются через адаптеры. Например, оркестратор не вызывает YooKassa или PayAnyWay напрямую. Он получает выбранный `adapterKey`, запрашивает адаптер у фабрики и вызывает общий метод `Send`.

## 4. Основная структура каталогов

Корневая структура проекта выглядит следующим образом:

```text
cmd/
  payment-gateway/
    main.go

internal/
  contracts/
  dto/
  httpapi/
  orchestrator/
  subsystems/

payment_gateway_tools/

README.md
go.mod
go.sum
docker-compose.yml
payment_gateway_schema.dbml
```

Назначение основных каталогов:

- `cmd/payment-gateway` содержит точку входа приложения;
- `internal/contracts` содержит интерфейсы подсистем;
- `internal/dto` содержит структуры запросов, ответов, статусы и модели отчетов;
- `internal/httpapi` содержит HTTP-обработчики для платежей, возвратов, отчетов, webhook-ов и служебных endpoint-ов;
- `internal/orchestrator/simple` содержит реализацию основного жизненного цикла платежа;
- `internal/subsystems` содержит конкретные реализации подсистем: адаптеры, антифрод, логирование, аутентификацию мерчанта, уведомления, маршрутизацию, секреты, хранилище, токенизацию и валидацию;
- `payment_gateway_tools` содержит PowerShell-скрипты, Postman-коллекцию и вспомогательные инструменты;
- `payment_gateway_schema.dbml` содержит DBML-описание фактической структуры базы данных.

## 5. Точка входа приложения

Точка входа находится в файле:

```text
cmd/payment-gateway/main.go
```

В `main.go` выполняется сборка всего приложения:

1. Создается logger на базе go-kit log.
2. Читается адрес HTTP-сервера из переменной `HTTP_ADDR`, по умолчанию используется `:8080`.
3. Инициализируются настройки транспортного и сетевого уровня.
4. Создаются реализации хранилищ и подсистем.
5. Если задана переменная `DATABASE_URL`, приложение подключается к PostgreSQL.
6. Если PostgreSQL недоступен или `DATABASE_URL` не задан, часть подсистем может использовать in-memory или no-op реализации.
7. Создается фабрика платежных адаптеров.
8. Создается оркестратор платежей.
9. Создаются HTTP handlers для платежей, возвратов, отчетов и webhook-ов.
10. Регистрируются маршруты HTTP API.
11. Запускается HTTP-сервер.

Важно, что `main.go` не содержит бизнес-логику платежа. Он играет роль composition root: создает зависимости и связывает подсистемы между собой.

Основные HTTP-маршруты регистрируются в `main.go`:

```text
POST /payments
GET  /payments/{payment_id}

POST /refunds/full/create
POST /refunds/partial/create
POST /refunds/status
POST /refunds/search

GET  /reports/transactions

POST /webhooks/yookassa
POST /webhooks/payanyway
POST /webhooks/digital-ruble
POST /sandbox/digital-ruble/scan

POST /merchant/webhook
GET  /health
```

## 6. Контракты подсистем

Файл:

```text
internal/contracts/interfaces.go
```

содержит центральные интерфейсы проекта. Эти интерфейсы задают границы между подсистемами.

Основные интерфейсы:

- `PaymentValidator` проверяет корректность платежного запроса;
- `AntiFraud` выполняет риск-анализ платежа;
- `Tokenizer` создает внутренний токен платежного средства;
- `PaymentAdapter` отправляет платеж во внешнюю платежную систему или эмулятор;
- `RefundAdapter` выполняет возврат платежа;
- `Notifications` отправляет уведомления интернет-магазину;
- `EventLogger` фиксирует события жизненного цикла платежа;
- `TransactionStore` сохраняет и читает платежные транзакции;
- `RefundStore` сохраняет и читает возвраты;
- `TransactionReportStore` формирует данные для отчетов;
- `PaymentRouteStore` хранит правила маршрутизации платежей;
- `PaymentRouter` выбирает платежную систему и adapter key;
- `WorkflowEngine` управляет сессией рабочего процесса;
- `RetryHandler` управляет повторными попытками вызова адаптера;
- `CallbackHandler` преобразует результат адаптера в итоговый `PaymentResponse`;
- `PaymentOrchestrator` описывает основной метод создания платежа.

Такой набор интерфейсов позволяет заменять реализации. Например, для тестов можно использовать in-memory store, а в реальном запуске подключить PostgreSQL. Точно так же вместо симулированного адаптера можно использовать YooKassa, PayAnyWay или адаптер цифрового рубля.

## 7. DTO платежного шлюза

Основные структуры данных находятся в каталоге:

```text
internal/dto
```

### 7.1. Запрос на создание платежа

Основной запрос описан структурой `CreatePaymentRequest`. Он включает:

- `merchant_id` - идентификатор мерчанта;
- `idempotency_key` - ключ идемпотентности;
- `payment_id` - внутренний идентификатор платежа;
- `current_status` - начальный статус платежа;
- `payment_info` - объект с деталями платежа.

`payment_info` включает:

- сумму и валюту;
- тип платежного метода;
- данные покупателя;
- описание платежа;
- временные метки.

Поддерживаемые способы оплаты:

```text
СБП
Банковская карта
Цифровой кошелек
Цифровой рубль
```

### 7.2. Ответ платежного шлюза

Ответ описан структурой `PaymentResponse`. Он содержит:

- идентификатор платежа;
- идентификатор мерчанта;
- ключ идемпотентности;
- текущий статус;
- платежную информацию;
- детали транзакции;
- объект ошибки, если операция завершилась неуспешно.

`TransactionDetails` содержит данные, которые появляются после обработки платежа:

- внешний идентификатор транзакции;
- платежная система;
- статус у провайдера;
- URL оплаты;
- QR-данные для цифрового рубля;
- внутренний token preview;
- результат антифрода;
- детали ошибки провайдера;
- технические поля цифрового рубля, например `participant_bank`, `schema_version`, `settlement_hint`.

### 7.3. Статусы платежей

В проекте используются следующие статусы платежа:

```text
CREATED
PENDING
CAPTURE_REQUESTED
CAPTURED
DECLINED
CANCELLED
FAILED
```

Назначение статусов:

- `CREATED` - платеж принят шлюзом и начал жизненный цикл;
- `PENDING` - платеж ожидает внешнего действия или подтверждения;
- `CAPTURE_REQUESTED` - шлюз вызвал адаптер и запросил проведение платежа;
- `CAPTURED` - платеж успешно проведен;
- `DECLINED` - платеж отклонен бизнес-логикой или провайдером;
- `CANCELLED` - платеж отменен или истек;
- `FAILED` - произошла техническая ошибка.

В проекте сознательно оставлен компактный набор статусов. Причины ошибок и детали провайдера передаются не через расширение набора статусов, а через объект `error` и поля `provider_error_code`, `provider_error_message`, `provider_status`.

### 7.4. Статусы возвратов

Для возвратов используются отдельные статусы:

```text
PROCESS_REFUND
SUCCESS_REFUND
FAIL_REFUND
```

Это позволяет отличать состояние возврата от состояния исходного платежа.

## 8. HTTP API

HTTP API сгруппировано в каталоге:

```text
internal/httpapi
```

Подкаталоги:

- `payments` - создание платежа и получение статуса;
- `refunds` - создание и поиск возвратов;
- `reports` - отчеты и статистика;
- `security` - транспортные и сетевые middleware;
- `webhooks` - входящие уведомления от платежных систем и демонстрационный webhook интернет-магазина.

API построено в стиле RESTful over HTTP. Запросы и ответы передаются в JSON. Для отдельных операций возврата также поддерживается form-data, чтобы удобнее тестировать запросы через Postman.

### 8.1. Создание платежа

Endpoint:

```text
POST /payments
```

Назначение: принять платежный запрос от интернет-магазина и запустить жизненный цикл платежа.

Обработчик:

```text
internal/httpapi/payments
```

Обработчик декодирует JSON, получает сведения о мерчанте из контекста middleware, проверяет право на операцию записи и вызывает оркестратор.

### 8.2. Получение статуса платежа

Endpoint:

```text
GET /payments/{payment_id}?merchant_id=...
```

Назначение: получить последнее сохраненное состояние платежа из `payment_transactions`.

Этот endpoint не пересчитывает платеж заново. Он читает сохраненный `PaymentResponse`, который был записан при создании платежа или после webhook-обновления.

### 8.3. Возвраты платежей

Endpoints:

```text
POST /refunds/full/create
POST /refunds/partial/create
POST /refunds/status
POST /refunds/search
```

Назначение: выполнить полный или частичный возврат платежа, получить статус возврата и найти возвраты по фильтрам.

Логика возвратов реализована отдельно от создания платежа, но использует те же общие инфраструктурные компоненты: хранилище, адаптеры, логирование.

### 8.4. Отчеты и статистика

Endpoint:

```text
GET /reports/transactions
```

Назначение: сформировать отчет по транзакциям. Поддерживаются фильтры по мерчанту, периоду, статусу, платежной системе и способу оплаты.

Отчет возвращает:

- список транзакций;
- общее количество;
- суммарный оборот;
- количество успешных и неуспешных платежей;
- группировки по статусам;
- группировки по платежным системам;
- группировки по способам оплаты.

### 8.5. Webhook-и платежных систем

Endpoints:

```text
POST /webhooks/yookassa
POST /webhooks/payanyway
POST /webhooks/digital-ruble
POST /sandbox/digital-ruble/scan
```

Webhook-и используются для обновления статуса платежа после внешнего события. Например, YooKassa и PayAnyWay сначала возвращают ссылку на оплату и статус `PENDING`. Окончательный статус приходит позже через webhook.

Эмулятор цифрового рубля использует sandbox endpoint, который имитирует сканирование QR-кода покупателем.

### 8.6. Демонстрационный webhook интернет-магазина

Endpoint:

```text
POST /merchant/webhook
```

Это не внешний API платежного шлюза для реального мерчанта, а демонстрационный endpoint внутри проекта. Он нужен, чтобы показать доставку уведомлений интернет-магазину без запуска отдельного приложения магазина.

## 9. Жизненный цикл платежа

Основной жизненный цикл реализован в:

```text
internal/orchestrator/simple/orchestrator.go
```

Последовательность обработки платежа:

1. Интернет-магазин отправляет `POST /payments`.
2. HTTP handler декодирует JSON и передает запрос в оркестратор.
3. Оркестратор проверяет обязательные идентификаторы: `merchant_id`, `idempotency_key`, `payment_id`.
4. Выполняется проверка идемпотентности по паре `merchant_id + idempotency_key`.
5. Если такая транзакция уже существует, возвращается ранее сохраненный ответ.
6. Создается workflow-сессия.
7. Платеж получает статус `CREATED`.
8. Записывается событие `payment_received`.
9. Модуль валидации проверяет платежные данные.
10. После успешной валидации платеж получает статус `PENDING`.
11. Записывается событие `payment_validated`.
12. Антифрод выполняет риск-анализ.
13. Записывается событие `fraud_checked`.
14. Если антифрод блокирует платеж, формируется ответ со статусом `DECLINED`.
15. Маршрутизатор выбирает платежную систему и adapter key.
16. Модуль токенизации создает внутренний токен.
17. Записывается событие `tokenized`.
18. Фабрика адаптеров возвращает нужный адаптер.
19. Оркестратор устанавливает статус `CAPTURE_REQUESTED`.
20. Вызывается адаптер платежной системы.
21. Результат адаптера преобразуется в `PaymentResponse`.
22. Итоговый статус сохраняется в PostgreSQL.
23. Записываются события результата обработки.
24. Сервис уведомлений отправляет webhook интернет-магазину.
25. Интернет-магазин может получить статус через `GET /payments/{payment_id}`.

Главная особенность: оркестратор не содержит кода конкретной платежной системы. Он управляет процессом, но делегирует внешние вызовы адаптерам.

## 10. Оркестратор платежей

Оркестратор расположен в каталоге:

```text
internal/orchestrator/simple
```

Файлы:

- `orchestrator.go` - основной жизненный цикл платежа;
- `router.go` - бизнес-маршрутизация платежа;
- `card_scheme.go` - определение схемы банковской карты;
- `workflow.go` - механизм рабочих процессов;
- `state_manager.go` - менеджер текущего состояния транзакции;
- `retry.go` - повторные попытки вызова адаптера;
- `callback.go` - преобразование результата адаптера в ответ шлюза;
- `types.go` - вспомогательные типы.

Разделение оркестратора на несколько файлов делает код более читаемым. Каждый файл отвечает за отдельный аспект процесса.

### 10.1. Основной файл orchestrator.go

`orchestrator.go` содержит структуру `SimpleOrchestrator` и метод `CreatePayment`.

`SimpleOrchestrator` хранит зависимости:

- validator;
- antiFraud;
- tokenizer;
- adapterFactory;
- notifications;
- transaction store;
- event logger;
- state manager;
- router;
- workflow engine;
- retry handler;
- callback handler.

Оркестратор создается через конструкторы. Есть конструктор с зависимостями по умолчанию и конструктор, который принимает конкретные реализации. Это удобно для тестирования и для запуска с PostgreSQL.

### 10.2. Идемпотентность

Перед выполнением платежа оркестратор проверяет, существует ли в хранилище транзакция с таким же `merchant_id` и `idempotency_key`. Если да, то возвращается уже сохраненный ответ.

Это нужно, чтобы повторный запрос от интернет-магазина не создал второй платеж во внешней системе.

### 10.3. Workflow и State Manager

Workflow engine хранит сессии обработки платежа. State manager хранит текущее состояние платежа. В текущей реализации эти компоненты простые и in-memory, но они выделены отдельными интерфейсами, чтобы показать архитектурную возможность замены.

### 10.4. Retry Handler

`retry.go` реализует повторные попытки вызова адаптера. Логика не повторяет платежи, которые уже перешли в нормальные бизнес-статусы вроде `PENDING`, `CAPTURED`, `DECLINED` или `CANCELLED`.

Повторные попытки предназначены в первую очередь для технических ошибок.

### 10.5. Callback Handler

`callback.go` преобразует низкоуровневый `AdapterResult` в итоговый `PaymentResponse`.

Именно здесь данные адаптера превращаются в унифицированный формат шлюза. Например, у YooKassa, PayAnyWay и цифрового рубля разные собственные ответы, но наружу шлюз возвращает единый `PaymentResponse`.

## 11. Валидация платежных данных

Модуль валидации расположен в:

```text
internal/subsystems/validator
```

Основной файл:

```text
payment_data_validator.go
```

Модуль выполняет две задачи:

1. Нормализует входные данные.
2. Проверяет корректность структуры и значений.

Примеры нормализации:

- обрезаются лишние пробелы;
- валюта приводится к верхнему регистру;
- email приводится к нижнему регистру;
- номер телефона очищается от пробелов, скобок и дефисов;
- номер карты очищается до цифр;
- строковые идентификаторы кошельков очищаются от лишних пробелов.

Примеры проверок:

- сумма должна быть больше нуля;
- валюта должна быть `RUB`;
- тип платежного метода должен входить в допустимый набор;
- телефон должен соответствовать формату российского номера;
- карта должна пройти проверку Luhn;
- дата карты должна быть в будущем;
- CVV должен состоять из 3 или 4 цифр;
- описание должно иметь допустимую длину;
- для СБП нужен телефон;
- для банковской карты нужны номер карты, дата и CVV;
- для цифрового кошелька нужен `digital_wallet_id`;
- для цифрового рубля нужен идентификатор кошелька или цифрового рубля.

Валидация встроена в общий жизненный цикл платежа. Если данные некорректны, платеж не передается дальше в антифрод, токенизацию и адаптер.

## 12. Антифрод

Модуль антифрода расположен в:

```text
internal/subsystems/antifraud
```

Текущая реализация является rule-based. Она не использует машинное обучение, но реализует набор детерминированных правил и счетчиков.

Результаты антифрода:

```text
PASSED
REVIEW
BLOCKED
```

Результат `PASSED` означает, что платеж может продолжаться. `REVIEW` означает подозрительный платеж, но в текущем прототипе он не блокируется. `BLOCKED` означает, что платеж должен быть остановлен и получить статус `DECLINED`.

Примеры правил:

- слишком большая сумма блокируется;
- повышенная сумма отправляется на review;
- подозрительные email, phone, description повышают риск;
- заблокированные кошельки или карты приводят к блокировке;
- частые попытки по одному и тому же email, телефону, карте или кошельку повышают риск;
- слишком много разных карт для одного email или телефона повышает риск.

Антифрод встроен до токенизации и до вызова адаптера. Это важно с архитектурной точки зрения: шлюз не должен отправлять явно рискованные платежи во внешнюю платежную систему.

## 13. Токенизация

Модуль токенизации расположен в:

```text
internal/subsystems/tokenizer
```

В проекте есть две реализации:

- `EphemeralTokenizer` - простая временная реализация без постоянного хранения;
- `PostgresTokenizer` - реализация с сохранением в PostgreSQL.

Токенизация создает внутренний токен вида `tok_...`, который используется внутри шлюза как абстракция над платежными данными. Внешние redirect-сценарии YooKassa и PayAnyWay не требуют передачи карты из шлюза провайдеру, потому что пользователь вводит платежные данные на стороне провайдера. Тем не менее внутренний токен нужен для унификации жизненного цикла.

`PostgresTokenizer` сохраняет данные в таблицу:

```text
payment_tokens
```

В таблице хранятся:

- hash токена;
- preview токена;
- способ оплаты;
- masked value;
- срок действия;
- служебные идентификаторы платежа.

Токенизатор не предназначен для хранения полного номера карты, CVV или полного токена в открытом виде.

## 14. Маршрутизация платежей

Маршрутизатор находится в:

```text
internal/orchestrator/simple/router.go
```

Это важная деталь архитектуры: `router.go` является частью оркестратора и принимает бизнес-решение о выборе провайдера. Он не является хранилищем маршрутов.

Инфраструктурное хранилище правил находится отдельно:

```text
internal/subsystems/routing/postgres_routes.go
```

Текущая логика маршрутизации:

1. Если способ оплаты - банковская карта, шлюз пытается определить схему карты по номеру.
2. Для карт МИР используется YooKassa.
3. Для остальных карт маршрутизатор обращается к таблице правил `merchant_payment_routes`.
4. Если правило не найдено, используется provider из переменных окружения. Если provider не задан, шлюз возвращает ошибку конфигурации вместо имитации платежа.

Определение карты реализовано в:

```text
internal/orchestrator/simple/card_scheme.go
```

Примеры:

- МИР: BIN/IIN 2200-2204;
- Visa: номер начинается с 4;
- Mastercard: диапазоны 51-55 или 2221-2720.

Для цифрового рубля маршрутизатор выбирает provider key `digital_ruble`.

## 15. Фабрика адаптеров

Фабрика адаптеров находится в:

```text
internal/subsystems/adapter/factory.go
```

Фабрика не принимает бизнес-решение о маршруте. Она только возвращает адаптер по provider key.

Поддерживаемые ключи:

```text
yookassa
payanyway
digital_ruble
simulated
```

Если для YooKassa или PayAnyWay не заданы переменные окружения, соответствующий адаптер не регистрируется как полноценный внешний провайдер. В этом случае попытка использовать его может завершиться ошибкой конфигурации.

Архитектурно фабрика отделяет выбор провайдера от создания конкретного клиента внешней платежной системы.

## 16. Адаптер YooKassa

Файл:

```text
internal/subsystems/adapter/yookassa_adapter.go
```

Адаптер YooKassa работает через HTTP API YooKassa.

Основной сценарий:

1. Шлюз получает платеж.
2. Оркестратор выбирает адаптер `yookassa`.
3. YooKassa adapter создает платеж с redirect confirmation.
4. Провайдер возвращает confirmation URL.
5. Шлюз возвращает интернет-магазину `payment_url`.
6. Пользователь переходит на страницу YooKassa и вводит платежные данные.
7. YooKassa отправляет webhook на `/webhooks/yookassa`.
8. Шлюз обновляет статус платежа.

Адаптер передает во внешний запрос сумму, валюту, описание, return URL и metadata. Metadata используется для связывания внешнего платежа с внутренним `payment_id`.

Внутренний токен шлюза не отправляется в YooKassa.

## 18. Адаптер PayAnyWay

Файл:

```text
internal/subsystems/adapter/payanyway_adapter.go
```

PayAnyWay adapter подключен как еще один российский платежный провайдер. Интеграция реализована через платежную форму MONETA.Assistant: шлюз не списывает деньги напрямую, а формирует ссылку с параметрами платежа и подписью.

Основной сценарий:

1. Шлюз получает платеж.
2. Маршрутизатор выбирает provider key `payanyway`.
3. Адаптер формирует параметры `MNT_ID`, `MNT_TRANSACTION_ID`, `MNT_AMOUNT`, `MNT_CURRENCY_CODE`, `MNT_TEST_MODE`.
4. В качестве `MNT_SUBSCRIBER_ID` передается внутренний `merchant_id`, чтобы webhook мог связать внешний callback с мерчантом.
5. Рассчитывается `MNT_SIGNATURE` на основе параметров платежа и кода проверки целостности данных.
6. Шлюз возвращает интернет-магазину `payment_url` и статус `PENDING`.
7. После тестовой оплаты PayAnyWay отправляет Pay URL callback на `/webhooks/payanyway`.
8. Webhook handler проверяет `MNT_SIGNATURE`, обновляет платеж до `CAPTURED` и отвечает XML-документом `MNT_RESPONSE`.
9. В XML-ответ добавляются атрибуты `INVENTORY` и `CLIENT`, чтобы PayAnyWay мог получить номенклатуру заказа для регистрации дохода самозанятого.

Для PayAnyWay используются переменные окружения:

```text
PAYANYWAY_MNT_ID
PAYANYWAY_INTEGRITY_CODE
PAYANYWAY_TEST_MODE
PAYANYWAY_PAYMENT_URL
PAYANYWAY_PAYMENT_UNIT_ID
PAYANYWAY_SNO
```

По умолчанию для СБП используется `paymentSystem.unitId=sbpc2b`, для банковской карты - `paymentSystem.unitId=card`.

В DTO платежа добавлено поле `payment_info.items`. Оно содержит позиции заказа: название, цену, количество, ставку НДС/признак без НДС, признак способа расчета, признак предмета расчета и внутренний идентификатор позиции. Если позиции не переданы, webhook PayAnyWay формирует одну позицию из описания и суммы платежа.

## 19. Эмуляционный адаптер цифрового рубля

Файл:

```text
internal/subsystems/adapter/digital_ruble_adapter.go
```

Цифровой рубль в проекте реализован как эмуляционный адаптер. Это связано с тем, что реальная платформа цифрового рубля Банка России не является открытым публичным sandbox API для произвольного подключения учебного проекта.

Адаптер цифрового рубля имитирует QR-сценарий оплаты:

1. Интернет-магазин отправляет платеж с методом `Цифровой рубль`.
2. Оркестратор выбирает `digital_ruble`.
3. Адаптер генерирует внешний идентификатор `drub_...`.
4. Генерируется QR ID `drqr_...`.
5. Генерируется строковый QR payload вида `drub://...`.
6. Генерируется QR-изображение в формате data URI.
7. В QR payload и `transaction_details` добавляются признаки цифрового рубля: категория товара, требуемая маркировка денег, идентификатор смарт-контракта и идентификатор платформенного SOAP-сообщения.
8. Шлюз возвращает платеж со статусом `PENDING`.
9. Интернет-магазин может отобразить QR-код пользователю.
10. Пользователь условно сканирует QR-код.
11. Sandbox endpoint `/sandbox/digital-ruble/scan` имитирует результат сканирования.
12. При успешном сканировании шлюз формирует SOAP/XML-сообщение `C2BPaymentCheck` и передает его в эмулятор платформы цифрового рубля.
13. Эмулятор проверяет смарт-контракт целевого расходования: хватает ли у кошелька покупателя цифровых рублей с подходящей маркировкой.
14. Если проверка пройдена, статус обновляется на `CAPTURED`; если маркировка не подходит или остатка недостаточно, платеж получает `DECLINED`.

В ответе адаптера используются поля:

- `qr_id`;
- `qr_payload`;
- `qr_image_data_uri`;
- `qr_expires_at`;
- `participant_bank`;
- `schema_version`;
- `settlement_hint`;
- `money_mark`;
- `smart_contract_id`;
- `smart_contract_result`;
- `smart_contract_reason`;
- `platform_message_id`;
- `platform_transport`;
- `platform_signature_type`;
- `payment_url`.

QR-код не является реальным QR цифрового рубля Банка России. Это демонстрационный формат, который показывает архитектурную готовность шлюза к QR-based payment flow.

Дополнительный пакет:

```text
internal/subsystems/digitalruble/
```

В нем реализованы:

- сопоставление категории товара с маркировкой цифровых рублей: `education -> EDUCATION`, `medicine -> HEALTHCARE`, `food -> SOCIAL_FOOD`, `transport -> TRANSPORT`;
- эмулятор кошельков с разными остатками маркированных средств;
- учебная проверка смарт-контракта `SC_MARKED_MONEY_V1`;
- построение и обработка SOAP/XML-сообщений платформы цифрового рубля.

Для прямой проверки SOAP-эмулятора добавлен endpoint:

```text
POST /sandbox/digital-ruble/soap
```

Этот endpoint принимает XML-сообщение `C2BPaymentCheck` и возвращает XML-ответ `C2BPaymentCheckResponse` с результатом `PASSED` или `DECLINED`. В промышленной интеграции здесь должны использоваться реальные сообщения платформы цифрового рубля и сертифицированная криптография; в проекте реализована учебная HMAC-подпись `HMAC-SHA256-EMULATION`.

## 20. Симулированный адаптер

Симулированный адаптер используется для локальных проверок и тестов. Он возвращает искусственный результат без обращения во внешнюю платежную систему.

Provider keys:

```text
simulated
```

Наличие симулированного адаптера полезно для разработки: можно проверить оркестратор, валидацию, антифрод, токенизацию, БД, логирование и уведомления без реальных ключей провайдеров.

## 21. Обработка webhook-ов

Webhook-обработчики находятся в:

```text
internal/httpapi/webhooks
```

Webhook-и нужны, потому что многие платежные системы работают асинхронно. При создании платежа шлюз часто получает только `PENDING` и URL оплаты. Окончательный результат появляется позже.

### 21.1. YooKassa webhook

YooKassa webhook принимает уведомление провайдера, извлекает внешний payment ID, metadata и статус. Если возможно, обработчик дополнительно запрашивает платеж у YooKassa API, чтобы получить актуальное состояние.

После обработки webhook шлюз обновляет сохраненный `PaymentResponse` в `payment_transactions` и отправляет уведомление интернет-магазину.

### 21.3. PayAnyWay Pay URL

PayAnyWay Pay URL принимает form-urlencoded запросы после успешной оплаты. Обработчик проверяет `MNT_SIGNATURE`, рассчитанный по `MNT_ID`, `MNT_TRANSACTION_ID`, `MNT_OPERATION_ID`, сумме, валюте, `MNT_SUBSCRIBER_ID`, `MNT_TEST_MODE` и коду проверки целостности данных. Если подпись корректна, платеж обновляется до `CAPTURED`, а PayAnyWay получает XML-ответ `MNT_RESPONSE` с кодом результата `200`, подписью ответа и номенклатурой заказа в атрибуте `INVENTORY`.

### 21.4. Digital Ruble sandbox webhook

Для цифрового рубля реализован sandbox endpoint, который имитирует результат сканирования QR-кода.

Возможные результаты:

- `captured`, `success`, `settled`, `paid` -> `CAPTURED`;
- `declined`, `rejected` -> `DECLINED`;
- `failed`, `error` -> `FAILED`;
- `expired`, `cancelled`, `canceled` -> `CANCELLED`.

При обработке проверяется соответствие `qr_id` и срок действия QR-кода.

## 22. Возвраты платежей

Модуль возвратов расположен в:

```text
internal/httpapi/refunds
```

Возвраты были добавлены как отдельная функциональность платежного шлюза. По логике они похожи на refund resource в платежных API: создается заявка на возврат, передается провайдеру, сохраняется статус и возвращается результат.

Поддерживаются:

- полный возврат;
- частичный возврат;
- получение статуса возврата;
- поиск возвратов.

Перед созданием возврата шлюз проверяет исходный платеж. Возврат должен выполняться только для платежа, который был успешно списан.

Данные возвратов сохраняются в таблицу:

```text
payment_refunds
```

Поля включают:

- `refund_id`;
- `payment_id`;
- `idempotency_key`;
- статус возврата;
- сумму;
- валюту;
- тип возврата;
- провайдера;
- внешние идентификаторы;
- ошибки провайдера;
- причину возврата;
- временные метки.

Адаптеры YooKassa, digital_ruble и simulated реализуют общий интерфейс возврата. PayAnyWay в текущей версии используется для создания платежей и не реализует refund-интерфейс.

## 23. Отчеты и статистика

Функциональность отчетов находится в:

```text
internal/httpapi/reports
internal/dto/report.go
internal/subsystems/storage
```

Отчет формируется на основе сохраненных транзакций. Он нужен, чтобы мерчант или администратор мог видеть историю платежей и агрегированную статистику.

Отчет поддерживает фильтры:

- `merchant_id`;
- дата начала;
- дата окончания;
- статус;
- платежная система;
- способ оплаты;
- limit.

Структура ответа включает:

- список транзакций;
- summary;
- группировку по статусам;
- группировку по платежным системам;
- группировку по способам оплаты.

В Postman для отчетов добавлена визуализация, которая показывает данные в виде таблиц, диаграмм и карточек статистики.

### 24.1. payment_transactions

Главная таблица платежей.

Назначение: хранить итоговое или последнее известное состояние платежа.

Ключевые поля:

- `merchant_id`;
- `payment_id`;
- `idempotency_key`;
- `status`;
- `payload_json`;
- `created_at`;
- `updated_at`.

В `payload_json` хранится сериализованный `PaymentResponse`. Это дает гибкость: DTO может развиваться, а таблица не требует отдельной колонки для каждого поля ответа.

Есть уникальность по:

```text
merchant_id + idempotency_key
```

Это используется для идемпотентности.

### 24.2. payment_tokens

Таблица внутренних токенов платежных данных.

- `token_hash`;
- `token_preview`;
- `payment_method`;
- `masked_value`;

### 24.3. payment_refunds

Таблица возвратов.

### 24.4. merchant_payment_routes

- `provider`;

- `active`.

Эта таблица не является маршрутизатором сама по себе. Она только хранит правила. Бизнес-решение принимает `router.go`.

### 24.5. notification_deliveries

Таблица доставок уведомлений интернет-магазину.

Хранит:

- ошибку;
- payload;
- количество попыток;
- временные метки.

### 24.6. Таблицы логирования

## 25. Хранилища

Реализации хранилищ находятся в:

```text
internal/subsystems/storage
```

Основные реализации:

- `PostgresTransactionStore`;
- `InMemoryTransactionStore`.

PostgreSQL-реализация используется в нормальном запуске проекта. In-memory реализация нужна для тестов, локальных экспериментов и случаев, когда база данных не настроена.

`PostgresTransactionStore` реализует несколько интерфейсов:

- хранение платежей;
- хранение возвратов;
- формирование отчетов.

Это удобно, потому что все эти операции работают с близкими таблицами и одной базой данных.

## 27. Сервис уведомлений интернет-магазина

Webhook URL задается через:


Сервис уведомлений отправляет наружу результат платежа. Например:

Он имитирует webhook интернет-магазина.

## 32. Как развивался код

Проект развивался итерационно.

На первом этапе был реализован базовый платежный шлюз:

- DTO платежа;
- HTTP endpoint создания платежа;
- простая валидация;
- простой оркестратор;
- in-memory store;
- simulated adapter.

Затем проект был декомпозирован на подсистемы. Были выделены интерфейсы в `internal/contracts`, чтобы отделить бизнес-логику от инфраструктурных деталей.

Следующий этап - подключение PostgreSQL. Появились таблицы:

- платежных транзакций;
- токенов;
- логов;
- уведомлений;
- мерчантов;
- маршрутов;
- возвратов.

После этого были добавлены реальные платежные адаптеры:

- YooKassa;
- PayAnyWay.

Их подключение потребовало реализации redirect/payment-form flow и webhook-обработчиков. Это изменило модель платежа: создание платежа часто стало возвращать `PENDING`, а окончательный статус начал приходить позже через webhook.

Далее был добавлен маршрутизатор платежей:

- банковские карты МИР отправляются в YooKassa;
- остальные карты могут использовать таблицу маршрутов или provider из переменных окружения;
- цифровой рубль отправляется в `digital_ruble`;
- СБП может маршрутизироваться в PayAnyWay через таблицу маршрутов.

Затем был добавлен модуль возвратов. Для него появились отдельные DTO, endpoint-ы, таблица `payment_refunds` и поддержка refund-операций в адаптерах.

Позже был добавлен цифровой рубль как эмуляционный QR-based adapter. Он генерирует QR payload, QR image data URI и поддерживает sandbox scan flow.

Также были добавлены отчеты по транзакциям и визуализации в Postman. Это позволило использовать Postman не только как клиент запросов, но и как демонстрационную панель для дипломного проекта.

Некоторые ранние или неиспользуемые элементы были удалены или упрощены. Например, неиспользуемые статусы платежей были убраны, а статусная модель стала компактнее. Неиспользуемый адаптер ТБанка был удален, чтобы код отражал реально поддерживаемые сценарии.

## 33. Главный поток данных в системе

В дипломе можно описать поток данных следующим образом:

1. Интернет-магазин формирует платежный запрос.
2. Запрос поступает в API-шлюз.
3. HTTP-слой декодирует JSON и передает DTO в оркестратор.
4. Оркестратор создает workflow session.
5. Валидатор проверяет корректность данных.
6. Антифрод оценивает риск платежа.
7. Маршрутизатор выбирает provider.
8. Токенизатор создает внутренний токен.
9. Фабрика адаптеров возвращает нужный adapter.
10. Adapter отправляет платеж во внешнюю систему или эмулятор.
11. Результат адаптера преобразуется в унифицированный `PaymentResponse`.
12. Хранилище сохраняет состояние платежа.
13. Логгер записывает события обработки.
14. Notification service отправляет webhook интернет-магазину.
15. При поступлении provider webhook статус платежа обновляется.
16. Интернет-магазин может запросить актуальный статус через API.

Этот поток хорошо соответствует архитектуре платежного шлюза, потому что показывает разделение между внутренней обработкой и внешними платежными системами.

## 34. Что важно подчеркнуть во второй главе диплома

## 35. Что не нужно делать главным акцентом

Вторая глава должна быть посвящена проектированию и реализации архитектуры. Поэтому не стоит превращать ее в главу по информационной безопасности.

Можно кратко упомянуть:

- аутентификацию мерчанта;
- разграничение ролей;
- токенизацию;
- маскирование данных;
- защищенное хранение отдельных секретов;
- проверки сетевого уровня.

Но основное внимание лучше оставить на:

- структуре кода;
- жизненном цикле платежа;
- взаимодействии подсистем;
- проектировании API;
- моделях данных;
- интеграции адаптеров;
- обработке callback/webhook;
- реализации цифрового рубля как эмуляционного сценария.

## 37. Краткое резюме архитектуры

Проект представляет собой модульный платежный шлюз на Go, в котором центральная бизнес-логика сосредоточена в оркестраторе, а внешние зависимости вынесены в отдельные подсистемы и адаптеры. HTTP API принимает запросы интернет-магазина, валидатор проверяет данные, антифрод оценивает риск, маршрутизатор выбирает провайдера, токенизатор создает внутренний токен, адаптер вызывает платежную систему, PostgreSQL сохраняет состояние, логгер фиксирует события, а сервис уведомлений отправляет результат интернет-магазину.

Архитектура поддерживает расширение: новый платежный провайдер можно добавить через новый adapter и регистрацию в factory. Новый способ оплаты можно добавить через DTO, валидатор, маршрутизатор и адаптер. Это соответствует цели дипломного проекта: разработать платежный шлюз с поддержкой интеграции внешних платежных систем и эмуляционного сценария цифрового рубля.
